# Замеры скорости

Решения об оптимизации — по цифрам. Как мерить — в [README](../README.md#замеры-скорости) (`yarn perf`).
Здесь — что мерили, что нашли и что изменилось после каждого этапа.

Числа одного компьютера между собой сравнимы, с другим компьютером — нет. Все замеры ниже — на одной машине:
облачный контейнер, Intel Xeon 2,8 ГГц × 4, 16 ГБ, без видеокарты (отрисовка — процессором), экран 1920×1080,
Electron 44.5.1 (Chromium 152). Обычный ноутбук быстрее по ядру, но слабый ноутбук или экран высокой чёткости
могут быть медленнее в 2–4 раза: `yarn perf --cpu 4` показывает, как будет на таком.

Что значат числа правки:

- **работа на шаг** — сколько браузер работает на одно движение мыши при перетаскивании (скрипты, стили, раскладка,
  отрисовка). Кадр — 16,7 мс при 60 кадрах/с: всё, что выше, — пропущенные кадры, движение рывками;
- **нажать** — от нажатия на объект до кадра, в котором его можно тянуть. 33 мс — нижняя граница самого замера
  (два кадра ожидания);
- **самый долгий кадр** после отпускания и отмены — заминка, которую видно глазом. 17 мс — кадр вовремя, 33 мс — один
  пропущенный, 100 мс и больше — заметная задержка.

## Исходный замер

Шаблон «Моя первая презентация» (31 слайд) и три слайда с объектами, которых в шаблоне нет (соединители,
диаграммы из текста, графики, — `tests/perf/objects`). Медиана пяти прогонов; полностью — колонка «Было» ниже.

- Запуск: первый после установки — 4,5 с до страницы выбора, обычный — 2,8 с.
- Студия на 31 слайде готова к работе за 1,9 с (второй раз — 1,3 с); загружается 280 файлов, 5 МБ.
- Перетаскивание держит 60 кадров/с, но схема «цикл» — 17 мс работы на шаг при бюджете кадра 16,7 мс.
- Нажатие на объект — 50–70 мс до начала движения; отпускание и отмена — заминка 80–120 мс; переход к слайду — 125 мс.
- Экспорт шаблона: HTML — 8 с и 3,8 МБ, PowerPoint — 8 с и 11 МБ, PDF — 8,5 с и 5,5 МБ.

## Этап 1: отклик студии (перетаскивание, отпускание, отмена, листание)

Жалоба: «подлагивает при движении схем», показ — без замечаний. Замер подтвердил: на этой машине перетаскивание
держит 60 кадров/с, но схема «цикл» тратила 17 мс на шаг (больше кадра — на ноутбуке слабее уже рывки), нажатие
на объект задерживало начало перетаскивания на 50–70 мс, отпускание и отмена давали заминку 80–120 мс, переход
к слайду — 125 мс.

Причины — по записи работы браузера (`yarn perf --trace`):

1. **Путь к объекту внизу холста** перезаписывался на каждое движение мыши, и каждый раз браузер пересчитывал
   раскладку всей студии (до 7 мс). Теперь — только когда путь изменился, не во время перетаскивания, и строка
   пути отделена от остальной раскладки (`contain`).
2. **Цвета акцента** после каждой правки записывались в стиль заново, тем же текстом: браузер пересчитывал стили
   всех элементов страницы (1180 элементов, 36 мс на отпускание). Теперь — только если цвета изменились.
3. **Панель свойств и лента** перестраивались в момент нажатия на объект (40–70 мс до начала движения). Теперь, пока
   кнопка мыши нажата на холсте, они ждут отпускания, а после него обновляются кадром позже, чем встаёт объект.
4. **Лента миниатюр** после каждой правки прокручивалась к текущему слайду, хотя он не менялся. Теперь — только при
   смене слайда.
5. **Плитки живых фонов** в панели свойств перерисовывались при каждом переходе к слайду: 39 сцен WebGL, на каждую —
   четыре пересчёта стилей ради цветов. Теперь цвета — один раз на ленту, рисуются только плитки на виду и в простое
   браузера, нарисованные запоминаются.
6. **Соединители** пересчитывались по одному: замер, запись, замер следующего — пересчёт раскладки на каждую линию.
   Теперь все линии слайда — разом за кадр (сначала замеры, потом записи), неподвижные не трогаются.
7. **Прилипание к направляющим** мерило все объекты слайда на каждом шаге; направляющие и рамка выделения
   перерисовывались, даже когда не менялись. Теперь — один замер на перетаскивание, запись — только изменений.

## Шаг A: свой сервер без Vite

Сервер вынесен из плагина Vite в `server/` ([docs/SERVER.md](SERVER.md)): основа для программы без Vite, MCP
и облака. На скорость не влияет и не должен: запуск, открытие студии и экспорт сверены с этапом 1 в одинаковых
условиях (`yarn perf --only start,open,export`, по три прогона) — диапазоны «до» и «после» совпадают,
экспортированный HTML совпадает побайтно.

## Живой фон: размер холста не на каждом кадре

Lighthouse (DevTools) на показе отметил принудительный пересчёт раскладки (forced reflow) в `backdrop.ts`: живой
фон мерил свою ширину на каждом кадре. Теперь — когда размер мог измениться (окно, масштаб холста студии, сам
фон) и раз в секунду. Lighthouse пересчётов больше не находит. Скрипты фона за 4 секунды показа
(`yarn test:perf`, по два прогона): «Сияние» 26 → 15 мс, «Частицы» 33 → 27 мс, «Сеть» 46 → 40 мс; кадры в секунду
на этой машине не изменились — их ограничивает рисование WebGL процессором (видеокарты нет).

Остальные цифры Lighthouse на `yarn dev` (FCP, LCP, «Minify JavaScript», «Avoid enormous network payloads») — про
загрузку по сети: сервер разработки отдаёт код несжатым и сотнями модулей, Lighthouse считает их по медленной сети.
Для программы и для файла, открытого с диска, это не те условия. Важны они для файла, выложенного в интернет
(3,8 МБ до первого кадра), и для облачной студии.

## Шаг Б: экспорт в HTML из готового проигрывателя

Раньше каждый экспорт в HTML заново собирал весь код показа (Vite, ~8 с), хотя от презентации в файле зависят только
данные. Теперь код показа — готовый проигрыватель ([docs/SERVER.md](SERVER.md#экспорт-готовый-проигрыватель)):
восемь вариантов (с правкой или только показ, с 3D, с формулами), установщик везёт их с собой, в `yarn dev` вариант
собирается один раз и лежит в кэше, пока не поменялся код. Экспорт только вкладывает в него данные и файлы.

Замер — «до» и «после» на одной машине, по три прогона (`yarn perf --only export`). Это другой облачный контейнер,
чем в таблицах выше: PowerPoint и PDF на нём медленнее и «до», поэтому сравнивать с ними нельзя.

| | До | После | |
|---|---:|---:|---:|
| HTML (шаблон, 31 слайд) | 7,87 с | 0,43 с | −95 % |
| HTML: первый экспорт после правки кода (`yarn dev`; в программе не бывает) | 7,87 с | 7,27 с | −8 % |
| PowerPoint | 10,9 с | 11,0 с | 0 % |
| PDF | 12,9 с | 12,8 с | 0 % |
| вес HTML | 3 988 669 байт | 3 953 525 байт | −35 КБ |

HTML стал легче: экспорт из студии собирал код как для разработки (сервер студии работает с
`NODE_ENV=development`, сборка его наследовала), и в файл попадала страница выбора презентаций. Теперь проигрыватель
всегда собирается как для выпуска.

Сверка со старым экспортом (шесть файлов: с правкой и без, с формулами, «Компактное», «Как на этом компьютере»;
`yarn build` до и после): данные презентации, исходная версия и блок лицензий совпадают побайтно, страница отличается
одной строкой `<meta name="slideria-deck">` (имя презентации; раньше оно было вшито в код) и атрибутом вида слайдов,
код — на ~300 байт (имя и вид он теперь читает из страницы). Файлы открываются без ошибок.

Варианты проигрывателя: только показ — 0,8 МБ, с формулами — +0,35 МБ, с 3D — +1 МБ, режим правки — +0,2 МБ. Все
восемь собираются за 34 с при сборке установщика.

## «Инструменты → Интеграции»: открытие студии не медленнее

Новая группа на ленте грузит один небольшой модуль, большая панель — только при первом открытии, сведения об
агентах — через 2,5 с после открытия, в простое браузера. Замер «до» и «после» на одной машине

|---|---:|---:|

| второй раз | 0,96 с (0,94–0,99) | 1,01 с (0,96–1,17) |
| загружено файлов | 281 | 282 |

## Шаг В: программа без Vite

Раньше программа запускала у себя сервер разработки Vite: при каждом запуске он готовил зависимости, а студию
отдавал по одному исходному файлу (~280 запросов). Теперь студия собрана заранее (`scripts/build.mjs --app`:
≈5 МБ, ≈50 файлов с отпечатком в имени, части студии — по мере надобности), сервер — одним файлом
([SERVER.md](SERVER.md)). Vite, esbuild и библиотеки страниц из установщика ушли (библиотеки — внутри сборки).

Замер — «до» (ветка `baseline-v12`) и «после» на одной машине, `yarn perf --only start,open --runs 3` (программа
из проекта: окно, сервер, страница выбора; студия на «Моей первой презентации» — шаблон, 31 слайд), медиана:

| | До | После | |
|---|---:|---:|---:|
| первый запуск: сервер готов | 1,19 с | 0,53 с | −56 % |
| первый запуск: страница выбора | 3,95 с | 0,65 с | −84 % |
| обычный запуск: сервер готов | 1,13 с | 0,53 с | −53 % |
| обычный запуск: страница выбора | 2,34 с | 0,65 с | −72 % |
| студия готова к работе | 1,37 с | 0,70 с | −49 % |
| студия, второй раз | 0,93 с | 0,42 с | −55 % |
| загружено при открытии студии | 282 файла, 5,3 МБ | 25 файлов, 2,2 МБ | |

Отклик правки не изменился (`yarn perf --only edit --runs 5`, 10 сценариев, сумма медиан): кадры те же (95 % — 16,7 мс,
кадров дольше 50 мс нет), работа браузера на шаг перетаскивания 62 → 57 мс, «отпустить» 840 → 806 мс, «отменить»
788 → 771 мс — разница в пределах разброса прогонов, в отдельных сценариях она в обе стороны.

Собранная программа (`node scripts/app-build.mjs --linux dir`), по четыре запуска своим замером — то же самое и размер:

| | До | После | |
|---|---:|---:|---:|
| запуск до страницы выбора, обычный | 1,9–2,2 с | 0,65–0,81 с | |
| студия открыта | 1,15–1,8 с | 0,64–0,76 с | |
| память программы (все процессы) | 850–970 МБ | 705–735 МБ | ≈ −15 % |
| папка программы | 414 МБ | 344 МБ | −70 МБ |
| из них код и библиотеки (`resources`) | 139 МБ | 70 МБ | −69 МБ |
| библиотеки (`node_modules`) | 122 МБ | 49 МБ | −73 МБ |

Самый первый запуск после сборки в обоих случаях дольше (5,2 и 5,7 с): файлы программы ещё не в памяти системы.
Сам установщик сжат, поэтому он легчает меньше, чем папка программы; его размер — со сборки под Windows.
`node_modules` программы теперь — только библиотеки сервера: `sharp` (37 МБ, сжатие картинок), `occt-import-js`
(чертежи STEP), `yaml`, `jszip`, `node-html-parser`, `@xmldom/xmldom` и их зависимости.
